# 从 0.8.x 迁移到 0.9.0

## 保留的工程与能力

工程 `schemaVersion: 1` 保持不变。已有来源、论点、资产、页面、48种局部卡片、自由构图、受控修改与撤销继续可用。新增 `storyboard` 是可选内容字段，保存、撤销和构建哈希均包含它。

DSH 工具从16个增加到19个：`academic_ppt_plan`、`academic_ppt_layouts`、`academic_ppt_deliver`。新增工具采用小参数入口，完整故事板契约通过 `contract(topic=storyboard)` 按需读取。

## 首次打开旧工程

1. 保留旧工程和导出文件，在原工程调用 `academic_ppt_context`，读取实际修订号和待处理项。
2. 继承用户已经给出的材料范围、篇数、全文要求、观看场景、设计方向和委托。旧 `consultation` 未标记交互模式时继续旧行为；整稿重构可显式使用 `interaction: checkpoints`。
3. 六页及以上整稿在最终交付前补回真实故事板：恢复现有问题、论点、图源与转场，不能把事后记录伪称为事先审批。请用户审阅尚未确认的科学取舍，已明确委托则自主处理。
4. 指定封面、最难正文和连续三页，查看当前实际 PPTX 样张并修复。旧稿升级可以从现有页面开始，不能只检查封面。
5. 重新构建和实际渲染。0.9.0 的渲染器版本变更使旧构建失效，这是对输出一致性的要求；旧文件不会被删除或覆盖。
6. 逐页登记当前画面的真实观察，最后用 `deliver` 生成新目录。

短于六页的短稿不强制添加故事板或三页样张。已选择使用故事板时，计划中的证据和条件仍会检查。不要为了规避整稿流程拆成多个小工程。

## 有意改变的行为

| 原行为 | 0.9.0 行为 | 使用影响 |
| --- | --- | --- |
| 草稿也名为 `report.pptx` | 草稿命名 `preview-not-for-delivery.pptx` | 自动化应读取返回的 `files.pptx`，不要硬编码旧路径。 |
| 各主题依次询问 | 新工程默认 `checkpoints`，成套方向讨论 | 一次真实回答可映射多个旧 topic，已有偏好和委托不重问。 |
| 非预设设计也要求卡片目录学习 | 可以记录 `pageRecipeIds` 或 `templateReferences` | 仍需真实预览、观察和适配；实际使用 card preset 时保留对应目录记录。 |
| 图像放入大框即可看似完成 | 报告真正 `imageBox`、缩放和标签高度 | 读数/比较的小图且标签未测会阻断，overview与可读的小图仍可使用。 |
| 计划容易在恢复中丢失 | 故事板独立核对实际资产、论点和必要主视图文字 | 删除 `visualPlan` 或 `drawings` 不能自动删除原科学要求。 |
| 导出文件可直接当成最终成果 | `deliver` 单独核验当前文件、渲染、逐页审查、计划与样张 | 有错误、草稿、旧哈希或未完成审查时不创建最终包。 |

`build(mode=review)` 仍可以为检查和样张生成文件。它表示“待审查的导出”，最终可用状态以 `check.verification.readyForDelivery` 和 `deliver` 为准。

## 样张确认的范围

`plan(kind=pilot-review)` 保存实际样张的 PPTX 哈希、渲染收据哈希、设计和关联证据指纹，以及真实用户选择或明确委托。增加其他页不会使不变样张失效。改变样张科学内容、来源、字体、色板、主线或计划后，需要重新复核。

最终逐页审查始终针对最终整稿的同一个 PPTX 哈希。样张通过不替代最终审查。对外部 Office/WPS 手工改动，插件会识别已导出文件不再一致；请保留手工文件，并在工程中重现需要的改动后生成新版本。

## 交付包与可恢复性

`deliver` 使用新目录，已有目录会拒绝覆盖。包内包含可编辑 PPTX、当前渲染预览、讲稿、证据、质量报告、审查记录和 `delivery-manifest.json`。渲染引擎产生 PDF 时一并保留。

`rebuild-project.json` 嵌入实际资产，可在新工作区继续编辑并重建。重建文件没有自动继承最终交付批准，需要重新渲染和检查。清单标明每个文件的摘要与源工程内容摘要，用于核对版本一致性。

插件无法证明 Agent 的陈述一定真实，也无法阻止宿主直接复制任何草稿。它提供可执行的最终入口、清晰状态和可复现证据；技能明确要求默认修复已发现的问题，不能用假记录或降低要求绕过。
