# 三个有价值的交互节点

让用户决定研究取舍与真正看到的表达效果。颜色、边界、语言、层次与封面属于完整方向，不拆成七轮参数问卷。作者负责把用户的意图变成可用页面，不能把日常对齐、裁切修复和取图责任推回给用户。

## 先复用已有信息

读取本次请求、反馈和工程中的决定，区分已确定、已明确委托、尚待讨论。用户提供优秀参考时，先指出实际观察到的特点，不让用户重新描述整套模板。继续工程或局部改稿不重新启动整稿问卷。

用户已说明“直接做”“按你推荐”“后续自行决定”等授权时，在其范围内继续。不能把没有偏好当成委托，也不能反过来忽略已有授权反复要求确认。

受众、时长、研究范围或材料缺失如果会实质改变成果，先完成能够独立推进的工作，再一次提出最有价值的少量问题。不要为形式收集无关偏好。

## 节点 A：共同确定故事线

初读来源后，给出这份报告的具体中心问题、推荐推进顺序、关键证据和缺口。有两种合理路线时，说明各自取舍，不给仅改标题的伪选项。

例如，同一综述可以按“观测到底约束了什么”组织证据，也可以按“泛化失败来自哪些假设”组织比较。应使用当前材料能支持的路线，不能为吸引注意而提前保证结论。

同时落实观看场景和密度：现场短讲、答辩兼复读、阅读材料。说明正文承载哪些必要条件，讲稿补充哪些解释。用户已明确这些信息时直接采用。

确认后写入 `brief.narrative` 与可读故事板。用户只同意顺序，不能被登记成同意尚未展示的视觉风格。

## 节点 B：看真实样张，选择成套方向

先准备封面、困难证据/机制页和连续三页；使用真实原图与实际信息量，实际导出并渲染。展示两套有意义的完整方向即可，不要求为没有争议的项目穷举所有组合。

每套方向一并描述：

- 证据与解释如何分配空间，如何支持用户确定的信息密度。
- 色板与颜色职责如何配合原图，字体如何区分题名、解释和数据标签。
- 边界、留白与层次怎样表达研究关系。
- 标题语言、封面和连续页面如何形成同一份报告。

提供明确推荐及代价，让用户选择 A、B 或具体局部组合。问题应是“哪一种更接近你要的学术汇报感”，同时指出可比较的具体差异，不能只丢下一句“觉得怎么样”。

一项完整方案选择可以同时覆盖 density、palette、shape、language、texture 和 cover 等字段。只有方案明确展示了这些取舍时，才把同一真实回答映射到相应主题。未展示的选项不能事后冒充用户选择；故事线授权也不自动变成视觉授权。

用户明确把设计交给作者时，自行决定并记录依据。仍然要制作和检查真实困难样张，委托省去的是不必要的等待，不是设计与验证。

## 节点 C：成品的最终使用

先修好已发现的问题，再展示可以使用的文件、路线摘要、时间预算和讲稿。只把真实需要用户专业判断的事项交给用户，例如是否保留某项有争议的研究解释，或是否将一段补充论证移入附录。

用户已请求成品时，不再询问是否允许导出。不能在 `needs-fix` 后交付失败稿并问“要不要做 v2”；裁切、重叠、缺字、漏证据和读不清的轴标签属于作者应完成的修复。

如果用户在这一节点提出修改，按影响范围处理，保留其他已确认项，不从节点 A 重新开始。

## 记录真实决定，兼容现有工程

先查询 `academic_ppt_contract` 的 design 与 preparation 契约。`academic_ppt_prepare` 只提供计划，不代替提问、用户回答或写入工程。将实际发生的选择通过受支持记录接口保存，并在故事板中保留节点、依据和预览路径。

| 字段 | 正确含义 |
| --- | --- |
| `mode: collaborative` | 用户参与重要取舍，作者负责日常实现 |
| `mode: delegated`、`delegation` | 用户明确委托整体设计，记录真实授权及范围 |
| `interaction: checkpoints` | 0.9.0 新工程按关键节点组织问题，一次成套方向可落实多个主题 |
| `interaction: topics` 或旧工程未标记 | 保留旧字段与主题流程兼容；整稿重新设计可按本次真实需求切换 checkpoints |
| `decisions[].topic` | 现有 density / storyline / palette / shape / language / texture / cover 是兼容存储字段，不是七次提问任务 |
| `status: proposed` | 建议尚未决定，不能证明已经问过或得到同意 |
| `status: confirmed` | `selected` 对应展示过的选项，`userResponse` 保留真实回答 |
| `status: delegated` | 在用户真实委托范围内采用的决定，同样保留依据 |
| `referencePaths` | 用户或作者实际看到的候选、样张或参考路径 |

选项可用 `{id,label,rationale}`，每轮通常给2–3项可比较选择；不要让用户先了解内部 preset ID 才能回答。允许自然语言组合修改。

保留每个主题当前有效决定及真实依据，不把尚在等待的消息写成“用户无回复”。一次回答覆盖完整方向时可以映射多个字段，无需重复询问。旧工程没有协商记录时按当前任务补充，不能倒填过去的对话。

故事线的具体论证与选择写入 `storyboard.decision`，实际样张的成套方向选择通过 `academic_ppt_plan` 的 `kind:pilot-review` 请求登记。后者只能在当前样张真实渲染且逐页 passed 审查后写入，不用纯聊天表态代替看图。

参考学习同时覆盖整页关系和组件细节。用 `referenceStudy.componentStudies` 记录具体参考页/卡、预览、边框填充、题签、间距与改造，用 `paletteRationale` 说明颜色职责；保留实际的 `pageRecipeIds/templateReferences/catalogIds` 和总体观察可帮助追溯。细读记录也可以独立提供对应来源与观察，不必重复抄录。新 checkpoints 六页及以上整稿（含计划页）只填整页ID不足以通过检查，自主drawings也不豁免学习；实际采用preset另需相应已查看`catalogIds`或同ID的`card-library`细读记录。参考记录不构成用户选择某方案的证明。

## 让决定落实到画面

将故事线写入 `brief.narrative`，方向写入 `design.direction`，色义写入 `palette/colorRoles`，字体和观看要求写入支持的 `system/projection`。记录用户偏好不会自动改变 PPTX，必须通过真实样张验证。

“丰富”优先指证据、局部比较、机制解释与多样阅读关系，不能靠增加长段落、阴影、图标和装饰提高信息量。“简洁”先删除同义复述，再重组说明，不能删掉决定结论含义的条件。

实际原图与方向冲突时先尝试保持科学含义的重排。只有涉及真正取舍，例如拆分过载页面导致超出页数约束，才向用户展示具体方案。普通断行、对齐、错字和裁切由作者自主修复。

明确密度后不要为消除检查失败降低阅读要求。草稿可以用于验证初始密度；一旦落实用户选择，修复应改内容组织与实现。颜色、圆角、语言和层级也遵循同样原则。用户否定样张的视觉效果时，将该方向视为待修订，回到实际参考页比较并制作具体修订样张；不以自动检查通过替代用户审美判断，也不把作者的修复决定记成用户已批准新方向。
