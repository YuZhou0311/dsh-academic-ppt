# 与用户共同确定学术汇报的感觉

新建整稿先建立设计对话，再批量排版。给出有内容依据的建议，把用户的选择落实到故事线、图文密度、字体与真实页面；不要把提问变成单独的问卷流程。查证、全文阅读和取图可在设计协商期间继续，已有证据工作不因视觉选择而丢失。

## 分阶段提问

先读取本次对话和已有工程，区分用户已确定、明确委托、需要讨论的事项。只问当前阶段还缺的选择，每轮通常1–3个相关问题。每个问题给2–3个易区分的选项，说明推荐项和具体影响，并允许用户用自己的话回答。不要只问“喜欢什么风格”，也不要把七个主题压成一个笼统的“你觉得如何”。

| 时机 | 要单独确定的主题 | 怎样提出有依据的选择 |
| --- | --- | --- |
| 开始规划，已知道题目与主要材料 | 信息密度 `density` | 推荐现场清晰、答辩兼复读或阅读材料中的适合项，解释图的可读大小、普通正文长度和讲稿分工。受众、时长未知时一并澄清必要约束。 |
| 初读材料，已有可支持的问题与图源 | 故事线 `storyline` | 用本稿具体研究问题提出不同推进顺序，例如从方法分歧进入证据，或从共同应用困难进入比较；说明各自重点与代价，不能提前保证未验证的结论。 |
| 准备代表页，已看来源图 | 配色 `palette`、形态 `shape` | 推荐2–3套正式学术配色并解释与原图变量色的协调；另问偏好干净直角、小圆角或更柔和边界，不用配色选择代替形态选择。 |
| 明确使用场景和视觉方向后 | 语言 `language`、层次质感 `texture` | 分别讨论精炼判断句/解释型学术语言，以及开放平面/细线浅底/克制层叠等方向。说明哪部分仍需保留完整限定。 |
| 封面与困难正文已有真实候选 | 封面 `cover`，复核先前密度与风格 | 展示两种实质不同的封面和代表正文，在相同观看尺度比较题名承托、元信息分组、图文大小和留白。明确问用户选哪种或怎样组合修改，再扩展全稿。 |

这些是决定出现的时机，不是固定轮次数。用户一次明确多个主题就合并记录；已知的听众、时长、模板与风格不重复问。用户提供图片时指出从图中读到的具体偏好，并询问尚不明确的取舍，不让用户重新描述整份参考。

## 等到真实回答，再记录决定

`academic_ppt_prepare`提供待问主题与建议，不会替作者提问。使用宿主实际提供的提问工具；没有专用工具时，以普通消息提出本轮问题并等待答复。刚发出问题、仍在同一轮执行中，不得将它记成“用户无回复”后替用户确认。与任务委派者协作时，向该请求方提问并等候其答复。

等待过程中可以完成不受选择影响的检索、原图盘点和暂定候选；不要把尚待讨论的配色或封面传播为全稿定稿。用户选择“按你推荐”“后续自行决定”等明确委托时，在其实际范围内继续，不为每张卡或每个坐标再问许可。无人可响应的批处理保留待确认状态和草稿，不能冒充协商完成。

模板问题沿用[template-learning.md](template-learning.md)，只问一次且不强制上传。没有模板不妨碍研究、内置参考学习和独立设计。用户只要求修改一页或纠正一处文字时，沿用现有方向；仅询问本次改动会实质改变而仍未确定的偏好，不重新启动整稿问卷。

## 保存可恢复的协商记录

先查`academic_ppt_contract({"topic":"design"})`与`academic_ppt_contract({"topic":"preparation"})`，使用当前契约的`consultation`。准备请求可接收同一记录，但`prepare`只返回计划与`designRecords`，不会替作者把回答写入工程。收到真实回答后，将返回的有效记录与当前`design`合并，通过`record`写入`design.consultation`；保留已确定的色板、模板和其他设计字段，并在`design-plan.md`保留简短协商表与预览路径。

| 字段 | 真实含义 |
| --- | --- |
| `mode: collaborative` | 新整稿默认，以用户实际回答完成各主题。 |
| `mode: delegated`、`delegation` | 用户明确把整体设计交给作者；记录实际委托语句及范围，不能用“缺少偏好”代替委托。 |
| `decisions[].topic` | `density`、`storyline`、`palette`、`shape`、`language`、`texture`或`cover`。 |
| `status: proposed` | 仍是待讨论建议；`recommendation`和`options`说明候选，不能证明已经问过或获得回答。 |
| `status: confirmed` | 保存`selected`与真实`userResponse`；需要时补`rationale`和已展示的`referencePaths`。 |
| `status: delegated` | 该主题由用户明确委托；同样填写`selected`与真实`userResponse`，说明作者依据委托采用的方向，不能把未回答主题自动转成委托。 |

选项用`{id,label,rationale}`描述。`selected`可记录用户的自由表达，不强迫其只选一个候选。每个主题只保留当前有效的一次决定；口头说明与记录必须一致，不能自动填写“已确认”。一次回答覆盖多个主题时可保留同一回答的对应部分，不补写未表达的偏好。

在正式构建前核对七个主题是否都有真实决定或明确委托。整体委托免去逐项确认，仍需作者完成设计稿、参考学习、候选与实际渲染。旧工程缺少协商字段时依据当前任务补充，不倒填过去发生过的对话。

## 把选择落实成可看的结果

在设计稿的协商表中，为每项选择写出具体落点：色板与色义、正文/图标签职责、封面候选、标题语言、卡片边界及一组代表页。摘要写入`design.direction`，故事线写入`brief.narrative`，颜色写入`design.palette/colorRoles`，字体写入受支持的`system/projection`。协商记录不会自动改画面。

用户偏好“字少一点、大一点”时，先展示删去同义复述后的代表页，保留比较条件、单位和边界，再提高实际字号；不要只增大文本框。用户偏好“丰富”时，优先增加有用图表、局部比较和解释关系，不能扩写长段落。封面选择不能决定所有正文都使用相同图文比例。

发现实际材料与已选方向冲突时，给出具体页面和两种处理，例如保持图完整并重组说明，或拆分一个过载任务。问会改变用户体验的取舍，常规对齐、行宽与错字由作者自行修好。用户后续反馈更新相关决定与页面，其余已确认项继续沿用。

对话完成后，继续原有研究、叙事、逐页设计、参考学习、候选比较、构建和审查流程。用户选择只能确定表达取舍，不能代替查证、读图或科学限定。

### 分批落实设计值

可以先记录真实回答，再把选择落实为实际配色、字号与密度。新工程的默认密度尚待落实时，制作 draft 或单独记录回答不会关闭首次密度选择；显式提供并确认的密度、已经落实的密度变化或成功的 review 构建会建立要求，不能为消除空区提醒随意降低。`prepare.designAdaptation.resolvedPreferences` 显示进入参考提示的已确认选择；检查它与讨论一致。原始回答保留在工程记录，生图提示仅承接所选设计和适配理由。
